# The projectfile Specification

**Version:** 1
**Revision:** 2026-08-17 (published)
**Canonical URL:** https://projectfile.org/spec/v1

______________________________________________________________________

## About this specification

### Abstract

This document defines **projectfile**, a single declarative file that carries a software project’s identity, legal, authorship, technical, and vendor-specific metadata in one place. The goal is to let a project ship one file instead of fifteen, while remaining open to tools the spec authors never imagined.

It reuses established standards — Schema.org, SPDX, SemVer, BCP 47 — for well-trodden concerns, and defines a reverse-DNS extension mechanism for everything else.

The document may be encoded as YAML (RECOMMENDED), TOML, or JSON; the on-disk filename identifies the encoding (`projectfile.yaml`, `projectfile.toml`, `projectfile.json`).

### Status of this document

Published. Version 1 of this specification is stable. The reserved field set is stable in intent; individual field shapes MAY change in minor revisions dated after this document’s revision header. Breaking changes will spawn a separate "version 2" document; version 1 will remain readable indefinitely.

This document is published at https://projectfile.org/spec/v1. The JSON Schema derived from this document is served at https://projectfile.org/schema/v1.json.

### Requirements language

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**, **MAY**, and **OPTIONAL** in this document are to be interpreted as described in [RFC 2119] when, and only when, they appear in all capitals, as shown here. [RFC 8174] clarifications apply.

## 1. Introduction

A typical software project today carries a dozen or more root-level metadata files:

- One or more language manifests (`package.json`, `pyproject.toml`, `composer.json`, `Cargo.toml`, `Gemfile`, `go.mod`, …).
- `LICENSE`, sometimes `LICENSES/` with REUSE-style per-file annotations.
- `README.md`, `CHANGELOG.md`, `AUTHORS`, `CONTRIBUTORS`, `MAINTAINERS`.
- `CITATION.cff`, `FUNDING.yml`, `.github/FUNDING.yml`, `codemeta.json`.
- `.gitignore`, `.editorconfig`, `.gitattributes`, `.nvmrc`, `.tool-versions`.
- Vendor config: `Jenkinsfile`, `.gitlab-ci.yml`, `.circleci/config.yml`, `renovate.json`, `dependabot.yml`.

These files duplicate identity, licensing, authorship, and dependency information, disagree subtly, and lock the project into whatever tool read each file first.

**projectfile** consolidates this information. Reserved fields cover concerns shared across every software project (identity, license, people, keywords, technologies, requirements). Reverse-DNS extension namespaces — `com.example.build`, `com.example.ci` — represented as nested mappings, carry vendor- or tool-specific data that cooperating consumers can read without stepping on each other.

The spec is deliberately extensible without a committee. Any author can claim an extension namespace (`org.example.my-tool`) and ship tooling that reads and writes it. An author needs no real or owned domain: any unique string following the segment rules is a valid namespace. The reverse-DNS form is a *convention* for avoiding collisions — "control" of a name means nothing more than picking a string others are unlikely to also pick — not an ownership requirement, and nothing verifies it. Consumers that do not recognize an extension namespace MUST preserve its values on round-trip and MUST NOT treat the document as invalid (the *peaceful cohabitation* rule, Section 3.7).

## 2. Terminology

- **Document** — the in-memory tree resulting from parsing a `projectfile.{toml,yaml,json}` file under this specification, regardless of the on-disk encoding.
- **Encoding** — one of TOML, YAML, or JSON. The file extension identifies the encoding (Section 3.1).
- **Producer** — any agent that writes or modifies a document.
- **Consumer** — any agent that reads a document.
- **Validator** — a consumer that verifies a document against the JSON Schema derived from this specification.
- **Coordinates** — the (`identity.namespace`, `identity.name`) pair that uniquely identifies a project within the ecosystem (Maven-style).
- **Reserved key** — a top-level key defined by this specification. Lowercase, single segment, no dots. `$schema` and `spec_version` are reserved by exception (see §3.4).
- **Extension namespace** — a nested-mapping path from the document root whose first segment is not a reserved key. The full path forms a reverse-DNS namespace (e.g., `com.example.build`). Each segment matches `^[a-z0-9][a-z0-9-]*$` and the path contains at least 2 segments.

## 3. Document format

### 3.1 filename and location

A document MUST be a file at the project root named:

- `projectfile.yaml` (YAML 1.2 encoding), or
- `projectfile.toml` (TOML 1.0 encoding), or
- `projectfile.json` (JSON / RFC 8259 encoding).

The file extension MUST match the actual encoding. A project is defined by the convention of its version-control system or packaging system; this specification does not redefine "project".

YAML is the **RECOMMENDED** encoding for new projectfile documents. TOML and JSON are accepted encodings for projects whose tooling already speaks one of those formats.

### 3.2 Encoding

A document MUST be encoded in UTF-8 [RFC 3629]. A byte order mark (BOM) MUST NOT be present. Line endings MAY be LF or CRLF; consumers MUST accept both.

### 3.3 Format

A document MUST be a syntactically valid file in one of the three accepted serializations:

- **YAML 1.2** [YAML-1.2]. The root MUST be a YAML mapping. Single-document files only; multi-document streams (`---` separators) are not documents under this specification.
- **TOML 1.0** [TOML-1.0]. The root MUST be a TOML table; the document is the root table.
- **JSON** [RFC 8259]. The root MUST be a JSON object.

> **Note on YAML 1.1 quirks.** Some widely deployed YAML libraries default to YAML 1.1 semantics, under which bare `yes`, `no`, `on`, `off`, `y`, `n`, and country code `NO` are coerced to booleans (the "Norway problem"). Consumers MUST use a YAML 1.2 parser (or a 1.1 parser with boolean coercion disabled). Producers SHOULD quote string values whose unquoted form would be ambiguous.

The three encodings carry the same document. Conversion between them is mechanical: a parser produces an in-memory tree; a serializer renders that tree in the target encoding. Any value expressible in one encoding MUST be expressible in the other two without semantic loss; producers MUST NOT rely on encoding-specific affordances (TOML inline-table syntax, YAML anchors and aliases, comment placement) to convey meaning.

### 3.4 Discriminator and schema linkage

Every document MUST identify itself as a projectfile-v1 document so that consumers can distinguish it from arbitrary TOML/YAML/JSON files that happen to share the filename. The mechanism differs by encoding so that mainstream editors and language servers provide schema-driven validation natively:

- **YAML and JSON.** A top-level key `$schema` whose string value is `https://projectfile.org/schema/v1.json`. This is the ubiquitous JSON Schema convention; it gives Visual Studio Code, JetBrains IDEs, `yaml-language-server`, and neovim immediate completion and validation.
- **TOML.** A top-of-file magic comment `#:schema https://projectfile.org/schema/v1.json` (the `taplo` convention) on the first line, AND a top-level key `spec_version` whose string value is `"1"`. The magic comment drives editor support; `spec_version` is the runtime discriminator a parser sees after stripping comments.

A file at one of the projectfile filenames that lacks the appropriate discriminator is **not** a document under this specification, regardless of name. Consumers MUST NOT interpret such a file as conformant.

The published JSON Schema enforces the **structural contract**: required fields, types, regular expression patterns on identifiers, and the closed shape of reserved fields. Validators MUST first parse the file according to its encoding and then evaluate the JSON Schema 2020-12 schema against the resulting in-memory tree. Semantic constraints expressed only in this prose (SHOULDs, RECOMMENDEDs, the cohabitation rules of Section 3.7) are out of scope for the schema and are the responsibility of consuming tools. Where the schema and prose disagree, the prose is authoritative and the schema is to be corrected.

### 3.5 Multiple files in one project

A project root MUST contain at most one `projectfile.*` file. If two or more are present (e.g., `projectfile.toml` and `projectfile.yaml` side-by-side), this is an error:

- Consumers MUST fail and SHOULD emit a diagnostic naming all the `projectfile.*` files found.
- Producers SHOULD NOT write more than one `projectfile.*` file per project. Tooling that converts between encodings (e.g., the sibling `projectfile/sync` project) SHOULD remove the source file after conversion or warn loudly that two files now coexist.

This rule exists to make pathological coexistence fail closed: rather than silently picking one file by a side-channel signal (such as modification time), a consumer surfaces the ambiguity so a human resolves it.

### 3.6 Top-level key classes

Every top-level key in a document belongs to exactly one of two classes:

- **Reserved**: `$schema` and `spec_version` (by exception, §3.4) and any key matching the pattern `^[a-z][a-z0-9-]*$` that is defined in Section 4. Reserved keys have fixed semantics defined by this specification. Unknown reserved keys (lowercase single-segment keys not defined in the version of Section 4 the consumer was built against) are accepted and preserved (peaceful cohabitation, §3.7).
- **Extension namespace root**: any key matching `^[a-z0-9][a-z0-9-]*$` whose value is a mapping representing the first segment of a reverse-DNS path. Each subsequent nested mapping key MUST also match `^[a-z0-9][a-z0-9-]*$`. The full path from root to leaf table MUST contain at least 2 segments. See §6 for naming and ownership rules.

A top-level key that matches neither class — for example, `Identity` (uppercase), `foo_bar` (underscore), `.hidden` (leading dot), or a numeric string — is malformed and MUST cause validation to fail.

The dotted-string form, in which an entire reverse-DNS path is packed into a single key (e.g., `"dev.acme.tool":` as one literal key), is **not** permitted. All extension namespaces MUST be represented as nested mappings. Rationale: nested mappings round-trip cleanly between TOML, YAML, and JSON; dotted-string keys do not (TOML interprets `[a.b.c]` as nesting; round-tripping a literal `"a.b.c"` key through TOML requires escaping that breaks editor tooling).

### 3.7 The handling rule (peaceful cohabitation)

This specification is designed for **peaceful cohabitation**: many independently developed tools should be able to read and write the same document without trampling each other, including across spec revisions.

The handling rule has three clauses:

- A consumer encountering an **unknown reserved key** (a single-segment lowercase key not defined in the version of Section 4 the consumer was built against) MUST ignore the key for interpretation purposes and MUST preserve it on round-trip. The consumer MUST NOT treat the document as invalid on this account, but MAY emit a warning. Rationale: minor revisions of this specification add reserved fields additively, and a consumer pinned to an older revision must still be able to read newer documents.
- A consumer encountering an **unknown extension namespace** (a nested-mapping path the consumer does not recognize) MUST preserve the entire subtree on any round-trip (read-then-write) and MUST NOT treat the document as invalid. Producers MUST NOT remove, rename, or modify nested-mapping subtrees outside their own namespace.
- A **malformed top-level key** (Section 3.6) MUST cause validation to fail.

Additionally, the mapping objects defined in Section 4 (identity, license, person, organization, link entries, repositories entries, copyright, requirements) accept additional keys beyond those listed in this specification. Consumers MUST preserve such keys on round-trip and MUST NOT treat the document as invalid for their presence. This allows producers to attach private annotations (e.g. ownership markers like `derived`) without spec changes, and allows future revisions of this specification to add fields additively.

"Preserve on round-trip" means the *values* of unknown keys and subtrees are carried through unchanged; encoding-specific formatting details (comment placement, key ordering, indentation style, quoting choices, inline vs. table layout in TOML) MAY change, since most parsers do not retain them. Producers that need to keep formatting intact SHOULD use a comment-aware parser.

The single way for an actor to forbid a key in a consumer is to *not implement it*. Spec-level rejection is reserved for malformed keys only.

### 3.8 Interpolation

A string value MAY reference another field of the same document. This is what lets a shared `includes` fragment (§4.9a) carry a value that resolves differently in every document that includes it — one fragment, no per-project text.

**Syntax.** A reference is `${` + a field address + `}`. The address is a dot-separated sequence of mapping keys, where:

- a key addressing a **list** MAY be followed by `[N]` (zero-based index, negative counts from the end), by `[key=value,…]` (the **first** entry whose named fields equal the given values), or by `[]` (every entry);
- a key addressing a **mapping of named keys** MAY be followed by `{key=value,…}` (**every** entry whose named fields equal the given values).

Equality is the only comparison. A key that itself contains dots (an extension namespace written in the flat form) is matched before the path is split, so `${org.projectfile.status}` addresses the same value regardless of which encoding of §6.2 the document uses.

A list operator applied to a mapping, or the mapping operator applied to a list, is a **malformed address**, not an absent value: the two containers are addressed differently and a consumer SHOULD say so rather than resolve to nothing.

The list and mapping selectors differ in how many entries they yield, and the difference follows from the containers. A list is ordered, so "the first entry matching" names a value an author can reason about. A mapping of named keys has no order the document defines, so there is no first entry to name; selecting from it therefore yields **every** match. A consumer that cannot represent several values MUST treat such a reference as unresolvable (below) rather than pick one.

**Timing.** Interpolation is resolved **after** include merge (§4.9a) and before the resulting values are interpreted as fields. A reference in an included fragment therefore resolves against the *including* document.

**Scope.** Only string scalars are interpolated. A reference that resolves to a mapping, a list, or nothing at all is **left verbatim**, as is a reference whose address is not well-formed.

A reference resolving to **several** scalars is left verbatim by a consumer substituting into a single string. A consumer whose output is a repeating structure — one line of a code block, one entry of a list — MAY instead emit one copy per value; where several such references appear in one string, the result is their cross product. Emitting one copy per value and silently substituting only the first are different behaviours, and a consumer MUST NOT do the latter.

The verbatim rule is what makes cohabitation work: a `${…}` belonging to another actor — a shell variable, a build-system variable, a CI matrix placeholder — is not a field address, so it survives untouched for that actor to resolve later. A consumer MUST NOT error on an unresolvable reference.

**Cycles.** A resolved value MAY itself contain references. A consumer re-resolves to a bounded depth of its own choosing and then leaves whatever remains verbatim. A consumer MUST NOT loop indefinitely.

**Escaping.** `$$` denotes a literal `$`; `$${x}` therefore renders `${x}` and is never resolved.

**Consumer obligation.** Interpolation is an interpretation-time mechanism, not a document-content one: a consumer MAY skip it entirely and MUST NOT fail on a document that uses it, per §3.7. A producer MUST NOT write resolved values back into the document in place of the references — the reference is the authored content.

Example (non-normative):

```yaml
identity:
  name: ubuntu
license:
  spdx: MIT
links:
  - type: source-code
    url: https://codeberg.org/b19/ubuntu
org:
  projectfile:
    readme:
      # → "https://img.shields.io/badge/license-MIT-blue"
      shields:
        - name: license
          img: https://img.shields.io/badge/license-${license.spdx}-blue
          href: ${links[type=source-code].url}
      installation:
        # → "docker run --rm registry.example/ubuntu:latest"
        commands:
          - docker run --rm registry.example/${identity.name}:latest
        # ${TAG} is a build-system variable, not a field address: left verbatim.
        postfix: Pin a release with ${TAG} instead of `latest`.
```

## 4. Reserved fields

### 4.1 `$schema` and `spec_version`

- **`$schema`**

    - **Type:** string (URI)
    - **Cardinality:** REQUIRED for YAML and JSON encodings, exactly one. Permitted but redundant in TOML (the magic comment carries the equivalent signal).
    - **Constraint:** when present, MUST equal `https://projectfile.org/schema/v1.json` for documents conforming to version 1 of this specification.

- **`spec_version`**

    - **Type:** string
    - **Cardinality:** REQUIRED for TOML encoding (paired with the `#:schema` magic comment), exactly one. OPTIONAL in YAML and JSON, where `$schema` already carries the version.
    - **Constraint:** MUST equal `"1"` for documents conforming to version 1 of this specification.

A document MUST satisfy the discriminator rule of §3.4 in its encoding. Validators MUST reject a YAML or JSON document missing `$schema`, and MUST reject a TOML document missing either the `#:schema` comment or `spec_version`.

### 4.2 `kind`

- **Type:** string
- **Cardinality:** OPTIONAL, at most one.
- **Default:** `SoftwareSourceCode`.
- **Values:** a [Schema.org type name](https://schema.org/SoftwareSourceCode) (drawn from the [Schema.org type registry](https://schema.org/docs/full.html)). For software projects, RECOMMENDED values are `SoftwareSourceCode` (the default — source code repositories, libraries), `SoftwareApplication` (end user applications), and `WebApplication`. Other Schema.org types MAY be used if justified by the project. The vocabulary is intentionally **open**: consumers MUST NOT reject a document for using an unrecognized type, and the JSON Schema does not constrain `kind` to a closed enum.

### 4.3 `identity`

- **Type:** mapping
- **Cardinality:** REQUIRED, exactly one.
- **Subkeys:**

| Key           | Type             | Cardinality | Description                                                                                                                                                                                                                                                  |
| ------------- | ---------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `namespace`   | string           | REQUIRED    | Reverse-DNS identifier of the owning entity. MUST match `^[a-z][a-z0-9-]*(\.[a-z0-9-]+)+$`. Example: `com.acme`.                                                                                                                                             |
| `name`        | string           | REQUIRED    | Project name. MUST match `^[a-z0-9]([a-z0-9-]*[a-z0-9])?$` (DNS-label shape).                                                                                                                                                                                |
| `version`     | string           | OPTIONAL    | Project version, as a SemVer 2.0.0 string per [SemVer]. prerelease and build-metadata suffixes permitted. Producers SHOULD treat this field as advisory; the authoritative version of an artifact remains its source-control tag or package-registry record. |
| `title`       | localized-string | OPTIONAL    | Human-readable title. See Section 7 for the localized-string type.                                                                                                                                                                                           |
| `summary`     | localized-string | OPTIONAL    | Single-sentence headline. SHOULD be ≤ 120 characters and SHOULD NOT contain line breaks. Distinct from `description`: the summary is the one-liner shown by package indices, app stores, and search results; the description is the longer prose.            |
| `description` | localized-string | OPTIONAL    | Longer human-readable description. May be multi-paragraph.                                                                                                                                                                                                   |
| `created`     | date             | OPTIONAL    | ISO-8601 calendar date of project inception. The interpretation of "inception" is producer-defined; conventional choices include the date of first commit, first publication, or directory creation.                                                         |
| `released`    | date             | OPTIONAL    | ISO-8601 calendar date on which the version named in `version` was released. Producers SHOULD update this field together with `version`. Consumers generating CITATION.cff or AppStream release entries SHOULD use this field for `date-released`.           |
| `modified`    | date             | OPTIONAL    | ISO-8601 calendar date of the last meaningful change to the project. Conventional choices include the date of the most recent non-trivial commit or the most recent release, whichever the producer considers more representative.                           |

The project’s **coordinates** — the (`namespace`, `name`) pair — uniquely identify a project within the ecosystem. Namespaces are *claims*, not proofs of ownership: nothing in this specification verifies that a producer controls the domain whose reverse form it uses. Consumers MAY use the coordinates as a deduplication key under that understanding (see Section 8).

Project URLs are not part of `identity` — they live in two dedicated top-level keys: `repositories` (§4.3a) for source-control endpoints, which carry structural attributes (branch, path, role) the rest of the URL vocabulary does not need; and `links` (§4.10) for every navigational URL with a `type` discriminator and an open vocabulary.

### 4.3a `repositories`

- **Type:** sequence of mapping
- **Cardinality:** OPTIONAL.
- **Item shape:**

| Key      | Type    | Cardinality | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| -------- | ------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `url`    | URI     | REQUIRED    | Clone endpoint. Any scheme Git accepts: `https://`, `git@host:path` (SSH), `git+ssh://`, `git://`, etc. The spec does NOT require an http-style scheme here — `repositories[]` carries the truthful clone endpoint, not the human-facing forge page.                                                                                                                                                                                                         |
| `type`   | string  | OPTIONAL    | VCS kind: `git` (default), `hg`, `svn`, `fossil`, `bzr`. Open vocabulary.                                                                                                                                                                                                                                                                                                                                                                                    |
| `path`   | string  | OPTIONAL    | Sub-directory inside the repository tree where this project lives. Used by monorepos.                                                                                                                                                                                                                                                                                                                                                                        |
| `branch` | string  | OPTIONAL    | Default branch on the remote. Producers SHOULD record this when known. Consumers MAY read it to tell a default-branch push from any other — a CI lowering distinguishing release builds from branch previews does exactly that — and, when it is absent, SHOULD fall back to a conventional default rather than fail.                                                                                                                                                                                                                                                                                                                                                                                       |
| `role`   | string  | OPTIONAL    | Open vocabulary; recommended values: `origin`, `mirror`, `archive`. The value `origin` is reserved: it marks the canonical entry. Exactly one entry MUST carry `role = origin` when the sequence has more than one entry; a sole entry is implicitly `origin`.                                                                                                                                                                                               |
| `issues` | boolean | OPTIONAL    | Marks the repository whose forge issue tracker is the project’s canonical bug tracker. At most one entry MAY carry `issues = true`. When present, consumers inferring issue-tracker URLs (the `links[type=bugs]` derivation described in §4.10) MUST emit a link only for this entry, even when other entries also point at forge hosts that provide issue trackers. When absent on all entries, the entry with `role = origin` (or the sole entry) is used. |

Consumers needing "the" clone URL (badges, package indices, the one shown in CITATION.cff `repository-code`) MUST pick the entry with `role = origin`, or the sole entry. When the picked entry’s URL is not http(s) and the consumer needs an http-style URL (e.g., to emit a CITATION.cff `repository-code` field or a `<url>` element that browsers can follow), the consumer SHOULD either (a) look up `links[type=source-code]` (§4.10) for the matching forge page, or (b) derive an http URL from the clone URL using the consumer’s own forge-host knowledge.

The forge **landing page** (the human-facing project page rendered by GitHub, GitLab, Forgejo, Gitea, sourcehut, etc.) is NOT a value in `repositories[]`. It is a `links[]` entry with `type = "source-code"` (§4.10) — distinct from the clone endpoint even when both are http URLs.

### 4.4 `license`

- **Type:** mapping
- **Cardinality:** OPTIONAL, at most one.
- **Subkeys:**

| Key      | Type                                       | Cardinality                      | Description                                                                                                                                                                                                                                                                                                                 |
| -------- | ------------------------------------------ | -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `spdx`   | string                                     | REQUIRED if `license` is present | SPDX license expression per [SPDX-EXPR]. Single identifiers like `MIT` are valid expressions. Compound expressions: `MIT OR Apache-2.0`, `(GPL-2.0-only WITH Classpath-exception-2.0)`.                                                                                                                                     |
| `covers` | string                                     | OPTIONAL                         | What corpus the SPDX expression applies to. Values: `project` (default) — applies to the entire source tree; `additions` — applies only to original work and packaging contributed in this repository, while bundled or wrapped upstream software retains its own licensing. See "Scope" below.                             |
| `file`   | string (path) or sequence of string (path) | OPTIONAL                         | Relative path(s) to license file(s) that ship alongside the document. A single string identifies one file; a sequence enumerates several (e.g., dual-licensed projects with both `LICENSE-MIT` and `LICENSE-APACHE`, or REUSE-style `LICENSES/*.txt` directories). Each entry MUST resolve per the path rules in Section 8. |

Copyright holders are NOT carried under `license`. They are assembled by consumers from the top-level [`copyright`](#44a-copyright) block and the per-person `from` / `to` fields under [`people`](#45-people) (entries whose `roles` contains `copyright`). This separation lets multiple consumers — LICENSE generators, SBOM tools, REUSE-style per-file headers — derive the same copyright lines from one source of truth.

#### Scope: `covers`

The `covers` subkey resolves an ambiguity in earlier drafts: an SPDX expression alone does not say *which corpus* it applies to. For an original-authorship project the answer is "everything in the source tree," but for a **distribution**, **container packaging repository**, **mirror**, or any project that bundles or wraps upstream software, the SPDX expression typically describes only what the project’s own contributors authored.

- `covers: project` (default) — the SPDX expression applies to the entire source tree. Equivalent to omitting `covers`. Appropriate for projects where contributors are the original authors of substantially all source.
- `covers: additions` — the SPDX expression applies only to original work and packaging contributed in this repository (e.g., Dockerfiles, build scripts, entrypoints, configuration glue, and any framework code authored alongside it). Bundled or wrapped upstream software retains its own licensing and is **not** relicensed by this declaration. Producers using `covers: additions` SHOULD enumerate per-artifact upstream licenses out-of-band (REUSE-style `LICENSES/` directory, populated `license.file` sequence, vendored `NOTICE` / `THIRD-PARTY` files, or similar) and SHOULD make the boundary explicit in `identity.description`.

Consumers generating SBOMs, attribution reports, or compliance metadata MUST treat `covers: additions` as a signal that `license.spdx` is **not** authoritative for the full image or distribution and MUST seek upstream license metadata from the bundled artifacts themselves.

Omitting the `license` field entirely signals that the licensing of the project is not declared in the document; it does **not** imply "no license" (which is a distinct legal concept) or public domain. Projects intending "no license granted" SHOULD state so using SPDX’s `LicenseRef-*` mechanism or the `NOASSERTION` identifier where appropriate.

### 4.4a `copyright`

- **Type:** mapping
- **Cardinality:** OPTIONAL, at most one.
- **Subkeys:**

| Key    | Type    | Cardinality | Description                                                                                                                                                                                                    |
| ------ | ------- | ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `year` | integer | OPTIONAL    | Default copyright year, applied when a person or entity with the `copyright` role lacks a `from` date. A single year — date ranges per holder are derived from the per-person `from` / `to` fields under §4.5. |

Copyright is conceptually separate from license: a project’s SPDX expression governs *how* downstream users may use the work, while the copyright lines record *who* holds rights and *for which years*. Earlier drafts collapsed both under `[license]` (the `holders` field), forcing every consumer to re-implement the parse of `"Copyright YYYY[-YYYY] Name <email>"` strings. The split puts the rights-holder data in one place and lets multiple tools — LICENSE generators, SBOM emitters, REUSE-style per-file headers — derive identical copyright statements from one source of truth.

Consumers assembling copyright lines:

1. Filter both `people` and `organizations` to entries whose `roles` (§4.5.4) contains `copyright`.
1. For each such entry, format `"Copyright {from}[-{to}] {flat-name}[ <{email}>]"`. `from` and `to` are taken from the per-entry fields (§4.5.1 for people, §4.5a for organizations); when `from` is absent, fall back to `[copyright].year`; when `to` is absent, the line ends with no upper bound (representing "present"). The flat name is synthesized per §4.5.3 for people; organizations use `name` directly.
1. Emit the resulting lines in document order across both lists.

A document MAY carry `[copyright]` without any `copyright`-role people (e.g., when only the year is recorded and the holder is implied by the project namespace), and MAY carry `copyright`-role people without a top-level `[copyright]` block (every such person supplies its own `from`). Producers SHOULD set at least one of the two so downstream consumers can render a meaningful copyright line.

### 4.5 `people`

- **Type:** sequence of mapping
- **Cardinality:** OPTIONAL.
- **Item shape:** each entry is a **person**. Entities (organizations, projects, teams) go in the separate `organizations` key (§4.5a).

#### 4.5.1 Person

#### 4.5.2 Flattening a person to a single-name string

Consumers emitting to formats that carry only a single name string (npm `author`, gemspec `authors[]`, AppStream `<developer_name>`, Maven POM `<developer><name>`) MUST use the person’s `display-name` when present. When `display-name` is absent, consumers SHOULD synthesize a flat name by concatenating, in order: `given-names`, `name-particle`, `family-names`, then a comma-space and `name-suffix`. Empty parts are skipped; remaining parts are joined with single spaces.

This default produces correct output for Western names (`Alice Example`, `Ludwig van Beethoven`, `Martin Luther King, Jr.`) and Iberian names with multi-part `family-names` (`Gabriel García Márquez`). It is **not** correct for cultures that order family name first (Hungarian, East Asian written in native order, Vietnamese), nor for mononyms with culturally significant ordering. Producers SHOULD set `display-name` explicitly whenever the default rule would misorder, mistransliterate, or otherwise misrepresent the name. The spec makes no attempt to encode locale-driven name-ordering rules; that responsibility lies with the producer who knows the person’s preferred presentation.

#### 4.5.3 `roles`

`roles` is a sequence of strings recording the roles this person or organization holds on the project. Recommended values: `author`, `maintainer`, `founder`, `contributor`, `reviewer`, `funder`, `packager`, `security`, `community`, `copyright`. The list is free-form; consumers MAY filter by role. Absent means unspecified. The vocabulary applies to both `people` and `organizations` (§4.5a); consumers filtering by role SHOULD iterate both lists. The `packager` role identifies a person or organization who assembles, distributes, or containerizes upstream software; it is distinct from `author` and the two MAY co-occur on a single entry. The `security` role identifies a member of the project’s security response team. A person entry with `roles: ["security"]` is a named individual on that team; an organization entry with `roles: ["security"]` represents the team itself (its `email` is the team inbox, its `url` is the team contact page). Consumers generating a `SECURITY.md` SHOULD filter by this role to populate the contact section. The `community` role identifies a person or organization responsible for community management and Code of Conduct enforcement. Consumers generating a `CODE_OF_CONDUCT.md` SHOULD filter by this role to populate the enforcement-contact section. The `copyright` role marks the person or organization as a rights-holder whose name appears on the assembled copyright line (§4.4a); the per-entry `from` / `to` fields supply the date range, falling back to `[copyright].year` when `from` is absent. For non-copyright-role entries, `from` and `to` remain valid historical metadata but do not contribute to copyright statements. `roles` is a projectfile extension over [CITATION.cff], which encodes the equivalent distinction by splitting authors, maintainers, and contacts into separate top-level sequences. When a consumer needs to pick a single contact for a role-targeted artefact (e.g. SECURITY.md, CODE_OF_CONDUCT.md) and no entry carries the artefact-specific role, it SHOULD fall back to any person or organization with `roles: ["maintainer"]`, then to any person or organization with an email address.

#### 4.5.4 Notes

The `people` field carries persons only. Organizations and other non-person actors go in `organizations` (§4.5a). A consumer needing only current maintainers SHOULD filter both lists by `"maintainer" in roles`. A consumer building a citation record SHOULD filter by `"author" in roles`. A person or organization SHOULD appear once even when holding multiple roles.

When migrating legacy inputs that carry only a single flat name (npm `author`, `git config user.name`, gemspec `authors[]`), producers SHOULD split the string with the heuristic: the last whitespace-separated token becomes `family-names`; the rest becomes `given-names`. A single-token name maps to `family-names` only (legal for mononymous people). A name in the comma form `Family, Given` MUST be split on the comma, with the part before becoming `family-names` and the part after becoming `given-names`. When the producer cannot confidently split, it SHOULD set `display-name` to the original string and leave `family-names` as the best-effort guess so §4.5.2 round-trips losslessly. When the source clearly identifies an organization (npm `author` containing an `Inc.`/`LLC`/`Foundation`/`Group` marker, or a CFF `- name:` entity), the producer SHOULD emit the entry under `organizations` instead.

The shape borrows from [CITATION.cff] so citation metadata can be derived mechanically. CFF `authors` merges both `people` and `organizations` filtered by role. projectfile does not mirror CFF’s full contact-field set (`address`, `city`, `country`, `region`, `post-code`, `tel`, `fax`, `location`, `date-start`, `date-end`); producers needing those fields SHOULD carry them under an extension namespace (e.g., `org.citation-cff`).

### 4.6 `keywords`

- **Type:** sequence of string
- **Cardinality:** OPTIONAL.
- **Values:** lowercase tags for discovery. Each tag MUST match `^[a-z0-9]([a-z0-9-]| [a-z0-9])*(?::[a-z0-9]([a-z0-9-]| [a-z0-9])*)?$`. Spaces are permitted between words (e.g. `open source`); consecutive or trailing spaces are not.

A keyword tag has one of two shapes:

- **Bare** — `logging`, `graph-database`, `static-site-generator`, `open source`. Equivalent to `package.json` `keywords` or GitHub topics: free-form thematic tags. Consumers MAY use them for indexing, search ranking, or display.
- **Namespaced** — `prefix:value`, where `prefix` and `value` each match the bare-tag pattern (spaces allowed in the value segment). Used to attach lightweight, classifier-style metadata without growing a structured `categories` field. Recommended (non-controlled) prefixes:
    - `topic:` — subject-matter classification (`topic:logging`, `topic:cryptography`, `topic:web-framework`).
    - `audience:` — intended consumer (`audience:developer`, `audience:scientist`, `audience:end-user`).
    - `status:` — maturity (`status:alpha`, `status:beta`, `status:stable`, `status:deprecated`).
    - `framework:` — primary framework (`framework:django`, `framework:rails`).

Producers MAY use other prefixes; consumers MUST NOT reject documents for using them, and SHOULD treat unknown prefixes as opaque tags. Tools mapping from PyPI trove classifiers, Cargo categories, or AppStream `<categories>` SHOULD emit namespaced tags rather than collapsing into bare keywords.

The `technologies` field (Section 4.7) carries the *technological* taxonomy; `keywords` carries the *thematic* and *classifier* one.

### 4.7 `technologies`

- **Type:** sequence of string
- **Cardinality:** OPTIONAL.
- **Values:** lowercase tags identifying technologies relevant to building, running, or consuming the project.

The `technologies` field is a flat set of tags. Tags typically identify languages (`python`, `rust`), runtimes (`node`, `jvm`), frameworks (`laravel`, `nextjs`), data systems (`postgres`, `redis`), and platforms (`docker`, `wasm`). Consumers MAY use `technologies` to generate `.gitignore`, select linters, scaffold CI pipelines, or present the project in search results.

The recommended vocabulary is published in `spec/technologies.yaml` in the specification repository. The vocabulary is **non-normative**: producers SHOULD prefer recommended tags so cooperating consumers behave consistently, but consumers MUST NOT reject a document for using a tag outside the recommended vocabulary. A consumer encountering an unknown tag MAY ignore it.

Producers needing a tag broadly applicable to other projects SHOULD contribute it to the recommended vocabulary by pull request (no gate-keeping; one-line rationale in the commit message). Producers with project-private taxonomy needs SHOULD use an extension namespace (e.g., `com.example.technologies`) instead of inflating the recommended vocabulary.

Each entry in the recommended vocabulary MAY carry an optional `use-cases` list of advisory tokens (e.g. `gitignore`, `dockerignore`, `editorconfig`) hinting at generation features a tag enables. These are **non-normative** and purely advisory: consumers MAY use them to offer such features, MAY ignore them, and MUST NOT reject a document on their basis. They live on the vocabulary entry, not in the projectfile document.

### 4.8 `requirements`

- **Type:** mapping
- **Cardinality:** OPTIONAL, at most one.
- **Subkeys:**

| Key        | Type                                                         | Cardinality | Description                                                                                                                                                                                                                                                                                                                      |
| ---------- | ------------------------------------------------------------ | ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `browsers` | sequence of string OR mapping of string → sequence of string | OPTIONAL    | Browser targets as [Browserslist] query strings. A flat sequence applies to all environments and generates a flat `.browserslistrc`. A mapping of lowercase environment names to query-string sequences generates per-environment `[section]` headers; environment names MUST match `^[a-z][a-z0-9-]*$`. Absent = unconstrained. |
| `runtime`  | mapping of string → string                                   | OPTIONAL    | Required runtime versions. Keys are lowercase identifiers (typically matching a technology tag: `node`, `python`, `php`, `ruby`, `go`, `rust`, `java`, `dotnet`). Values are version ranges in SemVer 2.0.0 syntax per \[SemVer\]: `">=8.5"`, `"^3.12"`, `"~1.0"`.                                                               |

`requirements` carries *runtime-targeted* constraints: which browser targets and runtime versions the project consumes. Platform targeting (operating system, CPU architecture) is a build/distribution concern rather than a runtime requirement, so it lives in the `org.projectfile.operating-system` and `org.projectfile.architecture` extension fields (§4.8a), not here.

Subkeys of `requirements` that correspond to a Schema.org property are named as the deterministic kebab-case of that property’s camelCase name, so no hand-maintained property map is needed. The single Schema.org export rule follows from this: `requirements` is flattened to the root — each of its subkeys becomes a root-level Schema.org property under the document’s `kind`. The `requirements.runtime` subkey deliberately stays a structured map (keyed runtime → version range), which is richer than Schema.org’s plain-text `runtimePlatform`; the plain-text form is *derived* from the map on export, not stored as a separate field.

`browsers` uses [Browserslist] query syntax. Producers MAY use any query string accepted by the Browserslist library; consumers MUST treat unknown or future query syntax as opaque and MUST NOT reject documents for using it. The `production` environment name carries special meaning in several bundlers (Vite, webpack, Parcel) and corresponds to the queries used when no `NODE_ENV` override is set. Producers SHOULD use `production` as the primary environment name where multi-environment entries are needed.

`runtime` ranges use SemVer syntax for portability across ecosystems. Producers whose ecosystem uses a non-SemVer scheme (PEP 440 epochs, Ruby `~>` operator, .NET floating versions) MAY emit native syntax in addition under an extension namespace (e.g., `org.python.pep440`). Consumers SHOULD treat the SemVer form as advisory and consult the language-native manifest for authoritative resolution.

### 4.8a Platform targeting (`org.projectfile.operating-system`, `org.projectfile.architecture`)

Platform targeting — which operating systems and CPU architectures a project builds or ships for — is declared under the spec’s own extension namespace, not under `requirements` (it is a build/distribution concern, not a runtime requirement). These two fields are the recommended, portable home for platform sets; they are extension-namespace data, so they are opaque to the core JSON Schema (§3.7) and are not flattened to Schema.org properties.

| Field                              | Type               | Cardinality | Description                                                                                                                                                                                                                                                                                                                         |
| ---------------------------------- | ------------------ | ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `org.projectfile.operating-system` | sequence of string | OPTIONAL    | Target operating systems. Recommended values follow the OCI image-spec platform vocabulary \[OCI-IMAGE-SPEC\]: `linux`, `darwin`, `windows`, `freebsd`, `openbsd`, `netbsd`, `illumos`, `solaris`, `aix`, `dragonfly`, `plan9`, `js`, `wasip1`. Absent = unconstrained (a consumer typically assumes `linux` for container builds). |
| `org.projectfile.architecture`     | sequence of string | OPTIONAL    | Target CPU architectures. Recommended values follow the OCI image-spec architecture vocabulary \[OCI-IMAGE-SPEC\]: `amd64`, `arm64`, `arm`, `386`, `riscv64`, `ppc64le`, `s390x`, `mips64le`, `loong64`, `wasm`. Absent = unconstrained (a consumer typically assumes the build host’s architecture).                               |

The lists are recommendations, not closed enums; consumers MUST NOT reject documents for values outside them. They mirror the vocabulary used by container tooling (Docker, Podman, Kubernetes) and Go’s `GOOS`/`GOARCH`.

When a project declares `architecture` without `operating-system`, a consumer building container images SHOULD assume `linux` as the operating system (the OCI default-platform convention). The cartesian product of the two lists is the project’s supported platform set; consumers lower it to their native form (e.g. `linux/amd64 linux/arm64`).

A consumer reading these fields SHOULD treat them as the project-wide platform set. Components of a build that target a *different* arch (e.g. a cross-compilation standard library bundled into every image arch, or a binary fetched for a wider arch set than the image builds) SHOULD be declared at that component, not by inflating the project-wide list — otherwise every platform-targeted component is expected to cover every declared arch.

### 4.9a `includes`

- **Type:** sequence of string
- **Cardinality:** OPTIONAL.
- **Values:** local paths or `https`/`http` URLs referencing projectfile documents to merge before reading.

Each entry is resolved in order and deep-merged into the base document: later entries win over earlier ones, and the base document always wins over all includes. The mechanism is encoding-agnostic — a YAML base may include a JSON remote fragment and vice-versa. Extension namespaces are merged recursively like any other mapping.

An entry is either:

- A **relative path** — resolved against the directory containing the projectfile. Path traversal rules from Section 8 apply.
- An **HTTP(S) URL** — fetched at read time. The URLs file extension determines the encoding (`.yaml`, `.toml`, `.json`). Network fetches are a dedicated consumer action; see Section 8.

Includes are resolved before any field is interpreted. A consumer that does not support includes MUST treat the document as valid and MUST NOT fail (peaceful cohabitation, §3.7), though its view of the document will lack the merged content.

Rationale: document composition is a core structural concern, not a tool-specific behaviour. Elevating it from an extension namespace (`org.projectfile.cli.includes`) to a reserved field makes it discoverable by every consumer and ensures the same merge semantics across all tooling.

- **Cardinality:** OPTIONAL.
- **Item shape:**

| Key         | Type             | Cardinality | Description                                                                                                                                                                                                                                                 |
| ----------- | ---------------- | ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `type`      | string           | REQUIRED    | URL category. Open vocabulary; consumers MUST NOT reject documents for unknown types. See recommended values below.                                                                                                                                         |
| `url`       | URI              | REQUIRED    | The URL.                                                                                                                                                                                                                                                    |
| `label`     | localized-string | OPTIONAL    | Human-readable display label.                                                                                                                                                                                                                               |
| `preferred` | boolean          | OPTIONAL    | Marks the canonical entry of its `type` when more than one shares the same `type`. `links` is the spec’s single typed navigational-URL surface. With the exception of source-control clone endpoints (which live in `repositories[]`, §4.3a, because they carry structural attributes — branch, path, role — that the rest of the URL vocabulary does not need). Funding configuration is handled by the `org.projectfile.funding` extension namespace, every URL associated with the project goes here under an open `type` vocabulary.

**Cardinality and selection.** A document MAY contain multiple entries with the same `type` (two bug trackers, two chat channels, multiple package-registry landings). When a consumer needs *the* URL of a given type (e.g., to emit `package.json`'s single `bugs.url`), it MUST pick: the entry with `preferred = true` if one exists for that type, else the sole entry of that type, else the first entry of that type in document order. Producers SHOULD set `preferred = true` only when more than one entry of the same type is present and the choice would otherwise be ambiguous.

**Consumer fallback chains.** When a consumer needs a URL of a given semantic role but the document does not carry an entry of the corresponding `type`, the consumer MAY fall back along a role-specific chain. The chains are consumer policy, not spec policy — emitters for `package.json` `homepage`, composer’s `support`, gemspec `metadata`, AppStream `<url>`, and CITATION.cff `url` each encode their own preferences. A reasonable default chain for a "project landing" slot is `links[type=homepage]` → `links[type=source-code]` → `links[type=documentation]`. Consumers SHOULD document their chains in their own changelogs; the spec does not enumerate them here.

## 6. Extension mechanism

### 6.1 Naming

An extension namespace is represented as a nested-mapping path from the document root. The path:

- MUST contain at least 2 segments.
- MUST have a first segment matching `^[a-z][a-z0-9-]*$` and that is **not** a reserved key.
- All segments MUST match `^[a-z0-9][a-z0-9-]*$`. The first segment additionally MUST start with a letter so that purely numeric values cannot be mistaken for extension namespaces.
- The full path, joined by `.`, MAY be the reverse of a domain the producer controls, optionally followed by additional segments scoping the extension within that domain; but any unique string following the segment rules is permitted. Reverse-DNS is a RECOMMENDED convention for collision-avoidance, not a requirement — ownership of the corresponding domain is neither verified nor required.

Examples (written as dotted paths; each maps to a YAML nested mapping, and likewise to JSON or TOML):

- `org.codeberg.alice.notes` — extension namespaced under a Codeberg user `alice`, using the `org.codeberg.<user>` convention.
- `com.example.build` — a hypothetical build-configuration extension under the neutral placeholder `example.com`.
- `com.weird-company.jenkins` — Jenkins configuration from `weird-company.com`.

Labels `com`, `org`, `net`, `io`, `dev`, and other top-level domains are permitted at the first position. For users who do not own a domain, namespacing under a forge where they have an account is a conventional, collision-free choice — `org.codeberg.<user>` (Codeberg), `com.github.<user>` (GitHub), `com.gitlab.<user>` (GitLab). These remain claims and conventions, not assertions of ownership: nothing verifies the account, and no account is required to use the form.

### 6.2 Cross-format representation (normative)

The same extension namespace expressed in each encoding:

#### YAML

```yaml
com:
  example:
    build:
      type: standard
      image: "ubuntu:24.04"
```

#### TOML

```toml
[com.example.build]
type = "standard"
image = "ubuntu:24.04"
```

#### JSON

```json
{
  "com": {
    "example": {
      "build": {
        "type": "standard",
        "image": "ubuntu:24.04"
      }
    }
  }
}
```

All three forms parse to the same in-memory tree. Conversion between encodings is mechanical and lossless at the document level. Producers MUST NOT use a single dotted-string key (e.g., a literal YAML key `"com.example.build":`) to represent an extension namespace; such forms are rejected (§3.6).

### 6.3 Consumer obligations

A consumer reading a document:

- MUST preserve unknown extension subtrees on any round-trip write (formatting may change, see Section 3.7).
- MUST NOT fail validation on an unknown extension namespace.
- MAY ignore the content of unknown extension namespaces when interpreting the document.

### 6.4 Producer obligations

A producer writing a document:

- SHOULD write every reserved field for which it has authoritative information.
- MUST NOT modify, rename, or remove subtrees in extension namespaces it does not own.
- MUST NOT alter values of reserved fields it does not control beyond what its task requires.
- SHOULD document its extension schema at a stable URL and reference it from the non-normative registry (§6.5).
- MAY version its extension independently of this specification (e.g., by including a `version` subkey under its namespace).

A **conformant producer** is one that obeys the rules above. The shorthand: *write everything you know, change nothing that isn’t yours.*

### 6.5 Registry

The specification repository maintains a non-normative registry at `spec/registry.yaml` listing known extension namespaces, their owners, and pointers to documentation. The registry is advisory — there is no gate-keeping. Contributing an entry is a pull request with a one-line purpose; the registry exists for discoverability, not permission.

Entries with a `shape` key point to an illustrative YAML fragment under `spec/shapes/{namespace}.yaml`. Shape files are not projectfile documents — they are syntax-valid YAML fragments showing the expected structure of the extension. They have no normative standing; the authoritative shape description is the documentation URL in the entry’s `docs` field.

A registry entry MAY also carry an optional `links` sequence — each entry a `url`, `title`, and `role` of `consumer` (a tool or project that reads the namespace), `producer` (one that writes or generates it), or `reference` (related documentation) — so readers can discover which tools work with a given extension namespace. These links are contributed by pull request and are purely advisory: they neither gate nor endorse, and an unrecognized role is rendered without error. This registry-level `links` surfaces *which tools consume or produce an extension namespace* and is distinct from the document-level reserved top-level `links` key (§4.10), which describes a *single project’s own* navigational URLs (and MAY be tool-generated, e.g., by the projectfile CLI or other generators).

### 6.6 Overlapping extensions

When two extensions describe the same operational concern (for example, two namespaces describing health-check endpoints), independent producers and consumers risk producing inconsistent or duplicated state. The recommended pattern is:

- Cooperating actors SHOULD agree on a **shared extension namespace** for the concern (e.g., a community-maintained `org.projectfile.health`) and treat vendor-specific namespaces as overlays that reference or extend it.
- A consumer encountering both a shared and a vendor-specific namespace SHOULD prefer the shared form for portable interpretation, and consult the vendor namespace only for vendor-specific behavior.
- The registry (§6.5) is the appropriate place to publish such shared namespaces.

This specification reserves no fields for these concerns; coordination is left to the community.

### 6.7 Extension authors’ guide (non-normative)

The extension mechanism is the part of projectfile that grows without anyone’s permission, and it costs nothing to start. Invent any namespace you like — no domain ownership, no registration, no committee — picking a reverse-DNS-style string (or `org.codeberg.<your-user>` if you have nothing else) only so it is unlikely to collide with anyone else’s. Publish your sub-schema at a stable URL and version it independently of this specification, so your tooling can evolve on its own clock. Ship tools that read and write your namespace, and rely on the *peaceful cohabitation* rule (§3.7): every other conformant tool carries your subtree through untouched, even tools written years before yours existed. Register the namespace in the non-normative registry (§6.5) — a one-line pull request — so others can discover it. That is the whole bargain: claim a name, document it, and your data rides alongside everyone else’s in the same file, forever, without coordination.

## 7. Localized strings

Several reserved fields (`identity.title`, `identity.summary`, `identity.description`) accept a **localized-string** value. A localized-string is a mapping from BCP 47 language tags [RFC 5646] to string values:

```yaml
title:
  en: "Snuggly Sunbeam"
  es: "Rayo de Sol Acogedor"
  uk: "Затишний Сонячний Промінь"
```

A localized-string MUST contain at least one language entry. The `en` entry is RECOMMENDED as a widely-understood fallback, but not REQUIRED — a project localized only to its primary audience’s language is valid.

For ergonomic compatibility with single-language sources (`package.json`, `pyproject.toml`, `Cargo.toml`), a **bare string** at the position of a localized-string is permitted as shorthand for a single-entry mapping under the BCP 47 language tag `und` (undetermined). Consumers MUST treat a bare string identically to:

```yaml
title:
  und: "Snuggly Sunbeam"
```

Producers SHOULD prefer the explicit mapping form when the language is actually known. Tooling migrating from single-language sources MAY emit either form, but writing `und` makes the lossiness explicit and is RECOMMENDED.

## 8. Security considerations

- **Namespace claims are unverified.** A producer writing `identity.namespace: org.example` asserts a relationship to `example.org` but offers no proof. Consumers MUST treat namespaces as identifiers, not as authentication, and MUST NOT confer trust on the basis of namespace value alone. The same applies to extension namespaces (Section 6).
- **No auto-fetch of URLs.** Consumers MUST NOT follow any `links[].url`, `repositories[].url`, extension-defined URL, or any other URL field automatically. Fetching is a dedicated action a consumer MAY take only with clear user consent.
- **Extension trust domain.** Extension namespaces are arbitrary data. A consumer that interprets an extension namespace does so under its own authority; the specification makes no claim about the trustworthiness of extension content. Consumers SHOULD validate extension contents against the extension’s own schema before acting on them.
- **No secrets.** Documents MUST NOT contain secrets (API keys, passwords, private keys). Secrets belong in out-of-band mechanisms (environment variables, secret stores, encrypted `.env` files). Producers SHOULD reject documents that include values matching common secret patterns; detection is best-effort.
- **Secret provisioning subtrees are NOT exceptions — they never carry real secrets.** A consumer MAY define a dev/CI secret-provisioning manifest (e.g. `org.projectfile.ci.secrets`) whose `value:` entries are dev defaults (`mariadb`) or explicit placeholders (`CHANGEME`) and whose `docker:` entries name a generator run at provisioning time (so no value is committed at all). Such a subtree is a *recipe for materializing* a `.secrets/` tree on a dev host or CI runner — it is NOT a store of production secret values. A real production secret is overlaid at runtime via the consumer’s deployment binding (e.g. `org.projectfile.ci`'s per-target `<target>.credentials` map, §6 extension schema), never committed in the document. A provisioning subtree carrying anything that looks like a real secret value SHOULD be rejected by producers as a likely §8 violation.
- **Interpolation reads, never executes.** A `${…}` reference (§3.8) resolves to a value already present in the merged document; it never names a file, a command, or a network location. A consumer MUST NOT extend the address grammar with anything that reads outside the document. Note that a remote include can plant a reference that resolves against the including document’s fields — that is the mechanism working as designed, and it is why §8’s no-secrets rule matters: a document that carries no secrets has none to leak into a fragment’s output.
- **Path traversal.** Path-valued fields (`license.file`) MUST resolve to a location inside the project directory after normalization. Consumers MUST reject paths that, after normalization, contain `..` segments crossing the project root, that are absolute, or that include a Windows drive letter (`C:\`, `\\?\`, etc.). Symlink behavior is consumer-defined: consumers operating in adversarial contexts SHOULD refuse paths whose resolution escapes the project directory; consumers operating on trusted local trees MAY follow symlinks.
- **Parser safety.** Each accepted encoding has its own parser hazards. YAML consumers MUST use a YAML 1.2 safe loader; custom tag handling (e.g., `!!python/object`, language-specific object construction tags) MUST be disabled. TOML consumers SHOULD reject documents with duplicate keys (the TOML 1.0 spec already requires this; some tolerant parsers do not). JSON consumers SHOULD use a parser that rejects duplicate object keys or warns about them.
- **Multi-file ambiguity.** Multiple `projectfile.*` files in one project root fail validation by default (§3.5). Because no file is selected by a side-channel signal such as modification time, there is no mtime-manipulation hazard for an attacker to exploit by swapping in a malicious sibling.
